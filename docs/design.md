## 1. 프로젝트 정의

교사가 쓴 세특 문장을 규정·문체·민감도 기준으로 검토하고, 학생 활동 기록으로부터 초안을 생성하며,
생성 결과를 다시 검토기로 검증하는 시스템.

### 1.1 목적

- 1차 목적: AI 강사 지원 포트폴리오. 코드잇 필수 역량 중 'NLP·LLM'과 'AI 모델 서비스 개발·배포' 두 항목 충족
- 2차 목적: 법인 포트폴리오로 단계적 확장. 처음부터 규모를 키우지 않는다
- 사업화가 아니다. 상용화·시장 차별성 기준으로 설계 판단을 내리지 않는다

### 1.2 세 기능

기능 이름은 무엇이 나오는지가 드러나도록 붙였다.

| 기능 | 입력 | 대조 문서 | 출력 |
|---|---|---|---|
| 세특 문장 검토기 (1순위) | 교사가 쓴 세특 문장 | 생기부 기재요령(규정집) + 교사 관습 규칙표 | 판정(위반·주의·권고) · 근거 · 수정안 |
| 세특 초안 생성기 (2순위) | 학생 활동 기록 | 없음. 생성한 뒤 검토기에 넣어 자동 검사한다 | 세특 문장 초안 |
| 학생 보완 안내 생성기 (3순위, 선택) | 학생이 제출한 코드·보고서 | 교육과정 성취기준 + 과제 요구사항·루브릭 | 학생에게 줄 보완 안내문 A4 1~2장 |

세 기능은 별개가 아니라 같은 구조를 세 곳에 적용한 것이다.
입력을 대조할 문서와 맞춰 보고, 어긋난 부분을 근거와 함께 알려준다는 점이 같다.

### 1.3 프로젝트 소개 문장

읽는 사람에 따라 두 가지를 쓴다. README 첫 문단과 강사 지원 시 프로젝트 설명에 공통으로 사용한다.

**① 일반 설명용 — README 첫 문단, 비개발자 대상**

> 세특을 쓸 때 지켜야 할 규정과, 규정집에는 없지만 현장에서 지켜지는 관습을 자동으로 확인해 주는 도구입니다.
> 어긋난 곳을 근거와 함께 알려주고 어떻게 고치면 되는지 제안합니다.

**② 기술 설명용 — 강사 지원서·면접, 개발자 대상**

> 입력 문장을 규정집과 관습 규칙에서 검색한 근거와 대조해, 위반·주의·권고 세 단계로 판정하고
> 근거와 수정안을 함께 출력합니다. 같은 구조를 세특 초안 생성의 사후 검증과 학생 산출물 피드백에도 적용합니다.

## 2. 보유 데이터와 자산 평가

| 데이터 | 누가 구할 수 있나 | 대체 가능성 |
|---|---|---|
| 공교육 생기부 규정집 (세특 부분 추출, 텍스트 추출 가능) | 누구나 | 공개 문서 |
| 세특 초안 (본인 작성, 특강 학생 대상) | 검색하면 유사 사례 다수 | 대체 가능 |
| 교사 관습 지식 (규정집에 없는 관행, 규정과 다른 실제 운용) | 현장 접근이 있는 사람만 | **대체 불가** |

**세 번째가 이 프로젝트의 유일한 대체 불가 자산이다.** 규정집으로 만든 검토기는 누구나 만든다.
'규정에는 있는데 실제로는 안 지키는 것', '규정에 없는데 다들 지키는 것'을 아는 시스템은 현장에 있는 사람만 만든다.

다만 이 지식은 현재 문서로 존재하지 않는다. 교사 관습을 규칙표로 옮기는 작업(8장 0-2)이 코드 작업보다 먼저다.

### 2.1 데이터 범위 제약

- 개발·평가 데이터는 본인이 담당했던 건으로 한정한다. 타 교사·타 학생 자료를 신규 수집하지 않는다
- 보유 초안에 학생 이름·학번·반 정보가 있으면 제거하고 일련번호로 치환한다
- 전처리 작업 내역을 기록해 둔다. 어떤 항목을 지웠고 몇 건을 처리했는지 한 줄로 남긴다
- 반입 금지: 타 교사 작성 세특 원본 / 식별정보 포함 원자료 / NEIS 화면·출력물

**기록을 남기는 이유**: 심사에서 "이 데이터는 어디서 났나"는 거의 확실히 나온다. 미성년자 개인정보이기 때문이다.
답이 준비되어 있지 않으면 프로젝트 전체가 감점 요인이 된다. 전처리 내역이 그 답변의 근거가 된다 (10.2 참조).

## 3. 시스템 구조

### 3.1 구성 요소

층으로 쌓인 구조가 아니다. 모듈 세 개와 그 모듈들이 읽는 자료로 나뉜다.

| 구분 | 내용 |
|---|---|
| 실행 모듈 | 세특 문장 검토기 · 세특 초안 생성기 · 학생 보완 안내 생성기 |
| 검색 자료 | 규정집 · 관습 규칙 · 교육과정 성취기준 |

> **검색 자료** — 원본 문서를 조각으로 자르고 숫자 배열로 바꿔 저장해 둔 것. 이 상태라야 검색이 된다.
> 검색 업계에서 index라고 부르지만 번호를 매기는 것과는 무관하다.

### 3.2 모듈과 자료의 연결

| 모듈 | 쓰는 검색 자료 |
|---|---|
| 세특 문장 검토기 | 규정집 + 관습 규칙 |<!-- 자료 위치: data/regulations/ · data/domain/ -->
| 세특 초안 생성기 | 없음. 프롬프트로만 동작한다 (근거는 4.2) |
| 학생 보완 안내 생성기 | 교육과정 성취기준 |

모듈 사이의 연결은 하나뿐이다. **생성기가 만든 문장이 검토기로 들어간다.**

### 3.3 검색 자료를 나눠 저장하는 이유

세 자료를 한곳에 섞지 않고 따로 저장한 뒤 따로 검색한다.

| 검색 자료 | 규칙 구분 | 출력에서의 표현 |
|---|---|---|
| 규정집 | 규정 규칙 | 근거로 인용 가능. 'O조 위반'이라고 판정한다 |
| 관습 규칙 | 관습 규칙 | 인용 불가. '일반적으로 이렇게 쓰지 않습니다' 수준의 권고 |
| 교육과정 성취기준 | 학생 보완 안내 전용 | '성취기준 O번 대비 미충족' 형태 |

한곳에 섞으면 검색 결과가 규정에서 나온 것인지 관습에서 나온 것인지 구분되지 않아, 관습을 조항처럼 인용하게 된다.
**근거 없는 조항 번호를 대는 도구가 되는 것이 이 프로젝트에서 가장 하면 안 되는 실수다.**

## 4. 기능별 명세

### 4.1 세특 문장 검토기 (1순위)

세 기능 중 유일하게 기술적으로 어렵다. 어필의 무게중심을 여기에 둔다.

#### 판정은 세 단계다

규정을 위반·정상 두 가지로만 나눌 수 없다. 기재요령에는 금지 항목 외에도
맥락에 따라 달라지는 조항과 정도의 문제인 원칙이 섞여 있다. 판정을 하나로 두면 이 둘을 담지 못한다.

| 판정 | 대상 규정 종류 | 출력 | 지표 |
|---|---|---|---|
| 위반 | 금지 · 수량 제한 · 형식 규정 | 조항 인용 + 수정안 | 검출률 · 오탐률 |
| 주의 | 조건부 허용 | '이 맥락에서는 확인 필요' + 조항 | 교사 동의율 |
| 권고 | 작성 원칙 · 관습 규칙 | '이렇게 쓰면 더 낫습니다' | 교사 동의율 |

**지표를 나누는 이유**: 위반은 정답이 명확해 검출률·오탐률로 잴 수 있다.
주의·권고는 사람마다 판단이 갈리므로 정답이 없다. 이쪽은 교사가 제안에 동의하는 비율로 잰다.

전부 위반·정상으로 판정하는 것은 규정을 읽지 않은 설계다. 세 단계로 나눈 이유를 말할 수 있는지가 심사에서 갈린다.

#### 입력 경로 2종

| | 외부 LLM 초안 붙여넣기 | 자체 생성 이어받기 |
|---|---|---|
| 문체 | 제각각 | 우리 프롬프트에서 나옴 |
| 위반 패턴 | 예측 불가 | 반복적 |
| 검토기에 주는 의미 | 다양한 입력에 견디는지 시험 | 생성 결과 자동 검증 |

**외부 LLM 경로가 실사용 시나리오에 더 가깝다.** 세특 생성 프롬프트 템플릿은 이미 유통되고 있고,
교사들은 이미 외부 LLM으로 세특을 쓰고 있다. 그렇게 나온 문장이 기재요령을 지켰는지는 아무도 확인해 주지 않는다.
이 도구가 그 자리를 맡는다.

#### 출력 형식

```
문장 / 판정(위반·주의·권고) / 규칙 구분(규정 규칙·관습 규칙) / 근거 조항 또는 관습 출처 / 수정안
```

#### 로그에 남길 것

- 입력 출처 (교사 직접 / 외부 LLM / 자체 생성) — 출처별 위반율 비교가 부가 실험이 된다
- 질의, 검색된 문서 조각 번호, 판정 결과, 소요 시간
- 호출당 토큰 수와 누적 비용

### 4.2 세특 초안 생성기 (2순위)

**RAG 방식이 아니라 프롬프트만으로 구현한다.**

> **RAG** — 검색해서 찾은 내용을 프롬프트에 끼워 넣고 그걸 근거로 답하게 하는 방식.
> 검색·끼워넣기·생성 세 단계를 합친 것이다. 검색만 하면 RAG가 아니다.

근거는 둘이다.

1. **생성 시점에는 검색 질의를 만들 수 없다.** RAG는 "무엇에 대해" 검색할지가 정해져 있어야 동작한다.
   검토기는 입력 문장이 있으니 그것으로 검색한다. 생성기에는 아직 문장이 없고 활동 기록만 있다.
   활동 내용과 규정 문언은 어휘가 겹치지 않아 엉뚱한 조항이 딸려 온다.
2. **문제의 종류가 다르다.** 모델이 규칙을 몰라서 어기는 것이 아니라 알면서 확률적으로 무시한다.
   조항을 더 넣어줘도 고쳐지지 않고, 프롬프트만 길어져 앞쪽 지시가 흐려진다.
   필요한 것은 생성 후의 자동 검사다.

**역할 분담**: 생성기는 자주 쓰는 규칙 20~30개를 프롬프트에 넣고 대략 맞게 쓴다.
조건부 허용과 작성 원칙까지 정밀하게 확인하는 것은 문장이 생긴 뒤, 검토기가 맡는다.

**검증 흐름**

```
학생 활동 기록 → 생성기 → 세특 문장 초안 → 검토기에 투입
                                              ↓
                          위반 있으면 재생성 / 없으면 완료
```

> **가이드** — 행동하기 전에 방향을 잡아주는 것. 여기서는 생성기에 넣는 프롬프트
> **센서** — 결과가 나온 뒤 규칙을 지켰는지 자동으로 검사하는 장치. 여기서는 세특 문장 검토기

생성 모델에게 자기 문장을 채점시키지 않는다. 별도의 규칙 검색기가 채점한다.
검토기를 새로 만들지 않고 그대로 재사용하므로 추가 구현 비용이 거의 없다.

- 병목은 구현이 아니라 입력 정의다. '학생이 무엇을 했는지'를 자유 텍스트로 받을지 항목 양식으로 받을지 먼저 정한다.
  양식을 정하는 것 자체가 도메인 지식의 증명이다
- 모델을 설정 파일에서 교체할 수 있게 만든다. 코드에 모델 이름을 박지 않는다.
  같은 프롬프트로 여러 모델을 비교한 결과가 곧 실험 결과가 된다

**부수 효과: 생성기가 검토기의 데이터 문제를 해결한다.**
보유 초안은 본인이 규정을 지키려고 쓴 것이라 위반 사례가 부족하다.
생성기가 뽑은 문장 중 규정을 어긴 것이 곧 검토기의 시험 데이터가 된다.

### 4.3 학생 보완 안내 생성기 (3순위, 선택)

학생이 제출한 코드나 보고서를 읽고, 그 학생에게 줄 보완 안내문을 만드는 기능이다.
성적·등급·점수를 매기지 않는다. '이 부분은 이렇게 보완하면 좋겠다' 형태의 안내다.

구조는 세특 문장 검토기와 같다. 대조할 문서를 넣으면 검색 기반으로 동작한다.

| 구성 | 내용 |
|---|---|
| 입력 | 학생 산출물. 1차는 텍스트만 (코드·보고서) |
| 대조 문서 | 교육과정 성취기준(공개 문서) + 본인이 만든 과제 요구사항·루브릭 |
| 출력 | A4 1~2매. '성취기준 O번에 비추어 이 부분이 미충족이므로 이렇게 보완하면 좋겠다' |
| 전달 | 학생에게 직접 나가지 않고 교사가 확인 후 전달한다 |

성취기준 대조는 교사가 원래 하는 일이고 근거가 명시되므로,
'AI가 학생을 판단한다'가 아니라 'AI가 기준과 대조해 보여준다'가 된다. 교사 보조 도구라는 위치가 유지된다.

**제약**

- 입력이 학생 산출물이라는 사실은 그대로다. 본인이 지도한 특강 학생 산출물로 한정한다
- 영상·이미지는 이미지 인식이 필요해 비용과 구현 복잡도가 한 단계 올라간다. 1차는 텍스트만
- 순서가 마지막인 이유는 리스크가 아니라 작업량이다. 성취기준 검색 자료를 새로 만들어야 하고 평가 기준도 따로 세워야 한다

## 7. 구현 스택

공고에 적힌 도구 이름을 쓰는 것이 목적의 절반이다.

| 구분 | 선택 | 근거 |
|---|---|---|
| 파이프라인 | LangChain | 코드잇·팀스파르타 공고 명시 |
| 벡터 저장소 | Chroma (로컬) | 설치 부담 없음. 데이터 규모가 작다 |
| 키워드 검색 | BM25 (rank_bm25) | 조항 번호·법령 용어 정확 매칭 |
| 결과 합치기 | RRF | 의미 검색 단독보다 성능이 낫다 |
| 임베딩 | KURE / KoE5 / BGE-m3-ko 중 택1 | 한국어 특화. 7.2 참조 |
| 생성 | 상용 LLM API (교체 가능하게 구성) | 세특 초안 생성기용 |
| 평가 | RAGAS | RAG 평가 도구의 사실상 표준 |
| 화면 | Streamlit | 코드잇 우대 항목 명시 |

용어:

> **벡터 저장소** — 문장의 의미를 숫자 배열로 바꿔 저장해 두고, 뜻이 비슷한 문장을 찾아주는 데이터베이스
> **BM25** — 단어가 실제로 일치하는지를 보는 고전적인 키워드 검색 방식. 조항 번호나 법령 용어처럼 정확히 같은 단어를 찾아야 할 때 강하다
> **RRF (Reciprocal Rank Fusion)** — 키워드 검색 결과와 의미 검색 결과의 순위를 하나로 합치는 방법
> **임베딩** — 문장을 숫자 배열로 바꾸는 모델. 이 배열이 비슷할수록 뜻이 비슷하다고 본다
> **RAGAS** — RAG 시스템의 검색·생성 품질을 항목별로 채점해 주는 오픈소스 평가 도구

### 7.1 왜 두 가지 검색을 함께 쓰는가

의미 검색만 쓰면 뜻이 비슷한 다른 조항을 끌어온다.
기재요령에는 조항 번호, 법령 용어, '교외 수상'처럼 정확히 일치해야 하는 문자열이 많다.
그래서 키워드 검색(BM25)을 함께 돌리고 두 결과의 순위를 RRF로 합친다.

### 7.2 임베딩 선택 시 주의

다국어 지원 표기는 그 언어의 텍스트를 처리한다는 뜻이지 그 언어에서 잘한다는 뜻이 아니다.
multilingual-e5-large 모델 설명서는 자원이 적은 언어에서 성능이 떨어질 수 있다고 직접 적고 있다.

| 모델 | 특징 |
|---|---|
| KURE (고려대 nlpai-lab) | 한국어 검색 특화. 저장소에 벤치마크 평균 결과 공개 |
| KoE5 | 사용 시 접두어 필수 (`query:` / `passage:`) |
| BGE-m3-ko | 짧은 문자열보다 긴 말뭉치에서 이점이 있다고 설명서에 명시 |

- 어느 모델이 내 데이터에 맞는지는 모델 설명서로 결정할 수 없다. 내 문서에서 질의를 뽑아 정답 문서를 표시해 두고 직접 재는 것 외에 방법이 없다
- 임베딩을 바꾸는 것은 검색 자료를 처음부터 다시 만드는 일이다
- 접두어를 빠뜨리면 사용법 자체가 틀린 것이다
- 한국어 특화 소형 모델은 512토큰을 넘는 문서에서 성능이 급격히 떨어진다. 조항 하나가 512토큰을 넘으면 항·호 단위로 더 잘게 나누는 규칙이 필요하다
- **첫 선택은 하나만 고르고 넘어간다.** 문서를 어떻게 자르느냐가 임베딩 모델 선택보다 성능에 더 영향을 준다. 모델 비교는 나중에 실험 항목으로 남기면 그 자체가 결과물이 된다

## 8. 작업 순서

0단계는 코드 작업이 아니라 자료 준비다. 그래서 1단계가 아니라 0단계로 둔다.

### 0단계 — 자료 준비 (선행)

작업이 둘이다. 코드보다 먼저다. 이것이 없으면 규정집만 쓰는 흔한 프로젝트가 된다.

#### 0-1. 규정 조항을 다섯 종류로 분류

기재요령은 금지어 목록이 아니다. 성격이 다른 조항이 섞여 있고, 종류에 따라 판정이 달라진다.

| 종류 | 예시 | 판정 | 프롬프트에 넣나 |
|---|---|---|---|
| 금지 | 교외 수상 · 어학점수 · 논문명 기재 | 위반 | 넣는다 |
| 수량 제한 | 글자 수 · 항목 수 | 위반 | 넣는다 |
| 형식 규정 | 주체 · 시제 · 문체 · 표기 방식 | 위반 | 넣는다 |
| 조건부 허용 | A는 되지만 B 맥락에서는 안 됨 | 주의 | 자주 쓰는 것만 |
| 작성 원칙 | 관찰한 사실 중심 · 구체적 근거 기술 | 권고 | 자주 쓰는 것만 |

분류하면 두 가지가 정해진다.

- 각 종류가 몇 건인지 → 생성기 프롬프트에 넣을 분량이 정해진다
- 조건부 허용이 실제로 얼마나 복잡한지 → 주의 판정을 따로 둘 필요가 있는지 확정된다

앞의 셋은 규칙으로 적을 수 있다. 뒤의 둘이 어렵다.
조건부 허용은 조합이 늘어나 목록으로 다 적을 수 없고, 작성 원칙은 위반·정상으로 나눌 수 있는 종류가 아니다.
그래서 판정을 세 단계로 둔다 (4.1 참조).

#### 0-2. 교사 관습 지식 규칙표 작성

- 먼저 보유 PDF에서 검색한다. 문언에 있으면 규정 규칙, 없는데 교사들이 지키면 관습 규칙
- 목표 20~30개 규칙. 이것이 관습 규칙 검색 자료의 원본이 된다
- 교사 인터뷰는 구조화된 질문지로 하고 답을 그 자리에서 적는다

규칙표 양식:

| 규칙 | 구분 | 근거 | 판정 |
|---|---|---|---|
| 향후 계획 서술 금지 | 규정 또는 관습 | 조항 번호 또는 '관습' | 위반 또는 권고 |
| (교사에게 들은 것) | 관습 규칙 | 출처: OO 교사, 날짜 | 권고 |

### 1단계 — 세특 문장 검토기

- 규정집을 조항 단위로 나눈다. 512토큰을 넘는 조항은 항·호로 더 나눈다
- Chroma에 적재하고 BM25 검색을 따로 만든다
- 두 검색 결과를 RRF로 합친다
- 관습 규칙은 별도 검색 자료로 둔다
- 판정 출력 형식을 구현한다. 위반·주의·권고 3단계 (4.1 참조)

### 2단계 — 평가셋 만들기

- 보유 초안에서 정상 문장을 추출한다
- 조항별로 위반 문장을 직접 작성한다. 위반과 정상을 대략 1:1로 맞춘다
- 위반 사례만 넣으면 전부 '위반'이라고 답하는 시스템이 100점을 받는다. 정상 문장이 있어야 오탐률이 나온다 (9.1 참조)
- 주의·권고 판정용 문장도 섞는다. 이쪽은 정답 대신 교사 동의 여부로 잰다
- 판단 불가 케이스를 10~15% 섞는다
- 목표 20~30건

### 3단계 — 세특 초안 생성기 기준선

> **기준선 (baseline)** — 비교의 출발점이 되는 가장 단순한 버전. 개선 효과를 재려면 먼저 이것이 있어야 한다
> **few-shot** — 프롬프트에 예시 몇 개를 함께 넣어 모델이 그 문체와 형식을 따라 하게 만드는 방법

- 입력 양식을 먼저 정의한다
- 예시 3~5건과 0-1에서 분류한 규칙 20~30개로 프롬프트 한 장을 만든다
- 20건을 생성한 뒤 검토기로 전수 채점한다
- 위반 건수와 위반이 나온 조항을 기록한다

**결과가 어느 쪽이든 산출물이다.** 위반이 0~1건이면 '단순한 방법으로 충분했다'를 숫자로 말할 수 있고,
5건 이상이면 '자동 검증이 필요한 정량 근거'를 얻는다.

### 4단계 — 검증 루프

검토기가 위반을 잡으면 그 조항을 프롬프트에 넣어 다시 생성한다.
위반 건수가 얼마나 줄었는지가 이 프로젝트의 대표 숫자가 된다.

### 5단계 — 배포

Streamlit 배포 + README 작성 + 시연 영상 녹화.

### 6단계 (선택) — 학생 보완 안내 생성기

성취기준 검색 자료를 구축한 뒤 텍스트 산출물 한정으로 착수한다.

## 9. 평가 설계

포트폴리오이기 때문에 더 필요하다. 사업이면 '고객이 쓴다'가 증거지만, 포트폴리오는 숫자 말고 증거가 없다.

| 대상 | 지표 | 정답이 있나 |
|---|---|---|
| 검토기 — 위반 판정 | 검출률 / 오탐률 / 판단 불가 정답률 | 있음 |
| 검토기 — 주의·권고 판정 | 교사 동의율 | 없음. 사람이 판단 |
| 검토기 — 검색 단계 | context recall | 있음 |
| 생성기 | 프롬프트 단독 위반 건수 → 검증 루프 후 위반 건수 | 검토기가 판정 |
| 공통 | faithfulness. 1.0 미만이면 실패 | 있음 |

용어:

> **검출률** — 실제 위반 중 시스템이 잡아낸 비율
> **오탐률** — 정상 문장인데 위반이라고 잘못 표시한 비율
> **교사 동의율** — 주의·권고 제안에 교사가 '맞다'고 답한 비율. 정답이 없는 판정을 재는 방법
> **context recall** — 답하는 데 필요한 문서 조각을 빠짐없이 가져왔는가
> **faithfulness** — 답변이 가져온 근거 안의 내용만 말했는가. 근거에 없는 말을 지어내면 떨어진다

**faithfulness만 기준이 다른 이유**: 세특에서 최악의 실패는 문장이 어색한 것이 아니라
학생이 하지 않은 일을 쓰는 것이다. 검출률처럼 '78%면 괜찮다'가 성립하지 않는다.

### 9.1 보고 원칙

- 절대 점수가 아니라 **변화량**으로 보고한다. 예: '문서를 조항 단위로 자르게 바꿨더니 context recall이 0.61에서 0.78로 올랐다'
- 판정 단계별로 나누어 보고한다. 위반 지표와 주의·권고 지표를 섞지 않는다
- 검색 단계와 생성 단계를 나누어 잰다. 실패했을 때 어느 쪽 문제인지 구분되어야 한다
- 평가셋에 정상 문장을 반드시 섞는다 (8장 2단계 참조)
- 자동 채점, 사람 판정, 모델 판정은 서로 대체재가 아니라 신뢰도가 다른 측정 방법이다

## 10. 어필 전략

### 10.1 강조 순위

심사자가 5분 안에 읽을 순서로 배치한다.

| 순위 | 강조 항목 | 왜 |
|---|---|---|
| 1 | 관습 규칙 검색 자료 | 현장 접근이 있는 사람만 만들 수 있다. 유일한 대체 불가 자산 |
| 2 | 판정 3단계 설계 | 규정을 위반·정상으로 나눌 수 없다는 것을 아는지가 갈린다 |
| 3 | 평가 설계와 변화량 | 튜토리얼을 따라 한 것과 갈리는 지점 |
| 4 | 규정 규칙과 관습 규칙의 분리 | 근거로 인용 가능한 것과 아닌 것의 구분 |
| 5 | 프롬프트 기준선과의 비교 | 단순한 방법부터 시도한 판단력 |
| 6 | 데이터 범위 제한 | 규제가 있는 분야를 다뤄 봤다는 신호 |
| 7 | 기술 스택 | 공고 요구 항목 대응 |

**강조하지 말 것**: 생성 문장의 품질, 화면 완성도, 확장성.

### 10.2 예상 질문과 답변

**왜 판정을 세 단계로 나눴나**

> 기재요령을 읽어 보면 금지 항목만 있는 것이 아닙니다. 맥락에 따라 달라지는 조건부 조항과,
> 정도의 문제인 작성 원칙이 섞여 있습니다. 이걸 전부 위반·정상으로 판정하면 조건부와 원칙을 담을 수 없어서,
> 위반·주의·권고 세 단계로 나눴습니다. 지표도 나눴습니다. 위반은 정답이 있으니 검출률과 오탐률로 재고,
> 주의와 권고는 사람마다 판단이 갈리므로 교사 동의율로 잽니다.

**왜 생성 기능에는 검색을 쓰지 않았나**

> 생성 시점에는 검색 질의를 만들 수 없기 때문입니다. 아직 문장이 없고 활동 기록만 있는데,
> 활동 내용과 규정 문언은 어휘가 겹치지 않아 엉뚱한 조항이 딸려 옵니다.
> 그리고 실제 문제는 모델이 규칙을 몰라서가 아니라 알면서 확률적으로 무시하는 것이라, 조항을 더 넣어도 해결되지 않습니다.
> 필요한 것은 생성 후의 자동 검증이라 판단해 검토기에 맡겼습니다.

**왜 실사용 배포를 하지 않았나**

> 미성년자 데이터가 들어가는 도구라 개인정보 처리 근거와 학교 승인이 선행돼야 하는데,
> 그건 기술 문제가 아니라 절차 문제입니다. 제가 담당했던 자료 범위 안에서 기능과 지표를 검증하는 데까지로 범위를 잡았습니다.

**이 데이터는 어디서 났나**

> 제가 담당했던 건이고 이름·학번·반 정보를 제거한 뒤 일련번호로 치환해 작업했습니다.
> 저장소에는 원본을 올리지 않았고, 타 교사·타 학생 자료는 수집하지 않았습니다.

## 부록 A. 용어집

| 용어 | 뜻 |
|---|---|
| RAG | 검색해서 찾은 내용을 프롬프트에 끼워 넣고 그걸 근거로 답하게 하는 방식. 검색·끼워넣기·생성 세 단계를 합친 것 |
| 검색 (retrieval) | RAG의 첫 단계. 이것만으로는 RAG가 아니다 |
| 검색 자료 | 원본 문서를 조각으로 자르고 숫자 배열로 바꿔 저장해 둔 것. 검색 업계에서 index라고 부르지만 번호를 매기는 것과 무관하다 |
| 문서 조각 (chunk) | 긴 문서를 검색 단위로 자른 한 덩어리. 이 프로젝트에서는 조항 하나가 기본 단위 |
| 임베딩 | 문장을 숫자 배열로 바꾸는 모델. 배열이 비슷할수록 뜻이 비슷하다고 본다 |
| 벡터 저장소 | 임베딩을 저장하고 뜻이 비슷한 문장을 찾아주는 데이터베이스. 여기서는 Chroma |
| BM25 | 단어가 실제로 일치하는지 보는 고전적 키워드 검색 방식 |
| RRF | 키워드 검색 결과와 의미 검색 결과의 순위를 하나로 합치는 방법 |
| 프롬프트 | 모델에게 주는 지시문 |
| few-shot | 프롬프트에 예시 몇 개를 함께 넣어 문체와 형식을 따라 하게 만드는 방법 |
| 가이드 | 행동하기 전에 방향을 잡아주는 것. 여기서는 생성기 프롬프트 |
| 센서 | 결과가 나온 뒤 규칙을 지켰는지 자동 검사하는 장치. 여기서는 검토기 |
| 기준선 (baseline) | 비교의 출발점이 되는 가장 단순한 버전 |
| 평가셋 | 성능을 재기 위해 정답을 미리 표시해 둔 시험 문항 모음 |
| 검출률 | 실제 위반 중 시스템이 잡아낸 비율 |
| 오탐률 | 정상인데 위반이라고 잘못 표시한 비율 |
| 교사 동의율 | 주의·권고 제안에 교사가 동의한 비율. 정답이 없는 판정을 재는 방법 |
| context recall | 답하는 데 필요한 문서 조각을 빠짐없이 가져왔는가 |
| faithfulness | 답변이 가져온 근거 안의 내용만 말했는가 |
| RAGAS | RAG 시스템의 검색·생성 품질을 항목별로 채점해 주는 평가 도구 |
| 규정 규칙 | 생기부 기재요령 문언에 명시된 규칙. 조항을 근거로 인용할 수 있다 |
| 관습 규칙 | 문언에는 없으나 현장에서 지켜지는 규칙. 인용 불가, 권고로만 표시한다 |
| README | GitHub 저장소를 열었을 때 첫 화면에 표시되는 설명 파일 |
| Streamlit | 파이썬 코드만으로 웹 화면을 만들 수 있는 도구 |
| 토큰 | 모델이 글을 처리하는 최소 단위. 한국어는 대략 한 글자에 1~2토큰 |
